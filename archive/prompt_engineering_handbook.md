## 第一部分：提示词基础原理

### 1.1 LLM 工作机制

大型语言模型（LLM）的工作机制可以概括为以下几个核心环节：

#### 1.1.1 预测原理

LLM 本质上是一个**概率预测引擎**。给定上文，它预测下一个 token 最可能是什么：

```
P(next_token | previous_tokens) = softmax(W · embedding(previous_tokens))
```

**关键理解**：
- LLM 不是"思考"，而是"统计性地预测"
- 没有真正的理解，只有模式匹配
- 输出质量取决于训练数据的分布和提示词的质量

#### 1.1.2 Transformer 架构核心概念

```
┌─────────────────────────────────────────────────────────────┐
│                    Transformer 架构流程                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Input Text → Tokenization → Embedding Layer               │
│                                    ↓                        │
│  ┌─────────────────────────────────────────────────┐        │
│  │           Multi-Layer Transformer Blocks         │        │
│  │  ┌──────────┐    ┌──────────┐    ┌──────────┐  │        │
│  │  │Attention │→→→│ Feed-Forward│→→→│ LayerNorm │  │        │
│  │  └──────────┘    └──────────┘    └──────────┘  │        │
│  │       ↑                                        │        │
│  │       └──── Self-Attention Mechanism ──────────┘        │
│  └─────────────────────────────────────────────────┘        │
│                          ↓                                  │
│  Output Projections → Logits → Sampling → Text Output      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Attention 机制的作用**：
- 让模型关注输入中相关的部分
- 自注意力（Self-Attention）：每个 token 可以"看到"所有其他 token
- 交叉注意力（Cross-Attention）：在解码时关注编码器的输出

#### 1.1.3 上下文窗口限制

| 模型 | 上下文窗口 | 实际可用（含输入） |
|------|-----------|-------------------|
| GPT-3.5 | 4K / 16K tokens | ~2,700 / ~10,800 words |
| GPT-4 | 8K / 32K tokens | ~5,400 / ~21,600 words |
| Claude 3 | 100K / 200K tokens | ~67,500 / ~135,000 words |
| Gemini 1.5 Pro | 1M tokens | ~675,000 words |

**重要影响**：
- 长提示词会挤占输出空间
- 末尾信息权重更高（Recency Bias）
- 关键指令应放在末尾或首尾重复

### 1.2 Token 概念详解

#### 1.2.1 什么是 Token

Token 是 LLM 处理文本的最小单位，**不是**单词或字符：

```
原始文本: "AI is amazing, isn't it?"

编码过程:
  "AI"     → token[0]
  " is"    → token[1]  
  " ama"   → token[2]
  "zing"   → token[3]
  ","      → token[4]
  " isn"   → token[5]
  "'"      → token[6]
  "t"      → token[7]
  " it"    → token[8]
  "?"      → token[9]

共 10 个 tokens
```

#### 1.2.2 Token 计算规则

| 内容类型 | Token 估算规则 |
|---------|---------------|
| 英文单词 | ~1.3 tokens/word |
| 中文汉字 | ~1.5 tokens/char（每个汉字≈1.5 token） |
| 代码 | ~1.2 tokens/token |
| 数字 | 每个数字单独编码 |
| 特殊符号 | 每个符号 1 个 token |

**快速估算公式**：
```
英文：token 数 ≈ 单词数 × 1.3
中文：token 数 ≈ 字数 × 1.5
```

#### 1.2.3 为什么了解 Token 很重要

1. **成本控制**：API 按 token 计费
2. **性能优化**：长上下文导致延迟增加
3. **提示词设计**：需要在 token 预算内传达清晰意图

### 1.3 生成参数解析

#### 1.3.1 Temperature（温度）

**作用**：控制输出随机性

```
Temperature = 0.0:  确定性输出，总是选概率最高的 token
Temperature = 0.7:  平衡（默认值），适合大多数场景
Temperature = 1.0:  完全随机，创造性输出
Temperature = 2.0:  极度随机，可能产生无意义输出
```

**场景建议**：

| 场景 | 推荐 Temperature |
|------|-----------------|
| 代码生成 | 0.1 - 0.3 |
| 数据提取 | 0.0 - 0.2 |
| 文案创作 | 0.7 - 0.9 |
| 创意写作 | 0.8 - 1.2 |
| 客服对话 | 0.5 - 0.7 |
| 数学/逻辑 | 0.0 - 0.1 |

#### 1.3.2 Top-P（核采样）

**作用**：动态限制候选 token 范围

```
Top-P = 0.1:  只从累计概率 10% 的 token 中选择 → 非常保守
Top-P = 0.9:  从累计概率 90% 的 token 中选择 → 平衡
Top-P = 1.0:  从所有 token 中选择 → 完全开放
```

**Temperature vs Top-P 对比**：

| 参数 | 工作方式 | 效果 | 典型值 |
|------|---------|------|--------|
| Temperature | 重缩放概率分布 | 平滑/尖锐分布 | 0.2 ~ 1.0 |
| Top-P | 截断低概率 token | 限制候选集 | 0.8 ~ 1.0 |

**最佳实践**：
- **不要同时调**：Temperature 和 Top-P 是互斥的调节方式
- 优先使用 Top-P（更稳定），或用 Temperature（更直观）
- 生产环境固定参数，便于结果可复现

#### 1.3.3 其他重要参数

```json
{
  "temperature": 0.7,
  "top_p": 0.9,
  "max_tokens": 1024,
  "frequency_penalty": 0.0,    // 降低重复（-2~2）
  "presence_penalty": 0.0,     // 鼓励新话题（-2~2）
  "stop": ["END", "\n\n"],     // 停止标记
  "seed": 42                   // 随机种子（可复现）
}
```

### 2.3 Chain-of-Thought（思维链）

**核心原理**：让模型在给出最终答案前，先展示推理过程。这对复杂推理任务效果显著。

#### 基础格式

```
问题：[复杂问题]

请逐步思考并给出答案。按照以下格式：

步骤 1：分析问题，识别关键信息
步骤 2：...
步骤 3：...
...
最终答案：[结论]
```

#### 实战案例 1：商业决策分析

```
某电商公司有以下数据：

| 指标 | Q1 | Q2 | Q3 | Q4 |
|------|-----|-----|-----|-----|
| 月均 GMV | 500 万 | 550 万 | 620 万 | 800 万 |
| 获客成本 | 50 元 | 55 元 | 60 元 | 80 元 |
| 用户留存率 | 35% | 33% | 30% | 28% |
| 客单价 | 120 元 | 125 元 | 130 元 | 150 元 |

问题：
1. Q4 的 GMV 增长主要来自什么因素？
2. 是否需要担心用户留存率下降？为什么？
3. 给出 Q5 的增长策略建议。

请逐步思考并给出答案。
```

**助手推理示例**：

```
**步骤 1：分析 GMV 增长来源**

GMV = 新客数 × 获客成本倒数 × 客单价
Q3→Q4 GMV 增长：620 万 → 800 万，增长 29%

因素分解：
- 获客成本上升：60→80 (+33%)，意味着相同预算下获客减少
- 客单价上升：130→150 (+15%)
- 用户留存率下降：30%→28%

→ 结论：GMV 增长主要来自客单价提升和可能的营销投入增加，
  而非自然增长。这是一个"付费换增长"的信号。

**步骤 2：评估留存率下降**

留存率从 35% 逐季下降到 28%，4 个季度下降 7 个百分点。

需要担心的理由：
1. 下降趋势持续 4 个季度，不是偶然波动
2. 获客成本在上升，如果留存也下降，LTV/CAC 可能恶化
3. Q4 留存 28% 意味着 72% 的用户在首次购买后流失

但需要注意：
- 需要对比行业基准（28% 在电商中可能正常）
- 需要区分新老用户的留存率

→ 结论：需要关注，但不必过度恐慌。建议深入分析原因。

**步骤 3：Q5 增长策略**

基于以上分析，建议：

1. 优化获客效率（优先级：高）
   - 分析 Q4 各渠道 ROI，砍掉低效渠道
   - 目标：将获客成本控制在 70 元以内

2. 提升用户留存（优先级：高）
   - 分析流失原因（调研/数据分析）
   - 启动会员体系/积分体系
   - 目标：将留存率稳定在 30%

3. 维持客单价（优先级：中）
   - 客单价已显著提升，不建议继续提价
   - 可考虑捆绑销售提升客单价

4. 拓展新增长点（优先级：中）
   - 考虑新品类或新市场
```

### 2.4 Self-Consistency（自我一致性）

**核心原理**：对同一个问题让模型多次生成推理路径，通过多数投票选出最一致的答案。提高复杂推理的准确性。

#### 基础格式

```
请用以下方法评估答案的可靠性：

1. 独立推理 3 次，每次得到答案
2. 比较 3 次答案的一致性
3. 如果一致，输出最终答案
4. 如果不一致，说明分歧原因并给出最可能的答案

问题：[复杂问题]
```

#### 实战案例 1：复杂计算验证

```
计算：(2/3 + 1/4) × (5/6 - 1/2) ÷ (3/8)

请按以下步骤操作：

**第 1 次推理：**
[独立计算过程]
结果：X1

**第 2 次推理：**
[独立计算过程]
结果：X2

**第 3 次推理：**
[独立计算过程]
结果：X3

**一致性检查：**
- 如果 X1 = X2 = X3，输出该答案
- 如果有差异，说明差异原因并给出最终答案

**最终答案：**
```

#### 实战案例 3：数据解释一致性检查

```

### 2.5 ReAct（Reason + Act）

**核心原理**：让模型在推理过程中主动使用外部工具（搜索、计算器、API 等），实现"思考-行动-观察"的循环。

#### 基础格式

```
你可以使用以下工具：
- search: 搜索互联网信息
- calculator: 计算数学表达式
- lookup: 查询数据库/知识库

任务：[需要外部信息的任务]

请按照以下格式进行：
思考：我需要知道...
行动：[工具名] - [参数]
观察：[工具返回结果]
...（重复以上步骤）
最终答案：[基于观察得出的结论]
```

#### 实战案例 1：实时信息查询

```
你可以使用以下工具：
- search: 搜索最新的新闻和信息

任务：查询 Tesla 公司 2024 年最新的股价走势和重大事件，
并分析这些因素对股价的影响。

请按照 ReAct 格式：
思考：我需要了解...
行动：search - [搜索关键词]
观察：...
最终答案：...
```

#### 实战案例 2：多步骤数据验证

```
你可以使用以下工具：
- calculator: 计算数学表达式
- lookup: 查询汇率数据库

任务：
中国某公司 2024 年在美销售额为 1200 万美元，
在中国销售额为 8000 万人民币。
计算该公司的全球总销售额（以人民币计）。

已知：
- 2024 年 5 月 1 日美元兑人民币汇率约为 7.2

请按照 ReAct 格式：
思考：我需要先将美元转换为人民币...
行动：calculator - 1200 * 7.2
观察：8640
思考：现在计算总销售额...
行动：calculator - 8640 + 8000
观察：...
最终答案：...
```

#### 实战案例 3：动态信息综合分析

```
你可以使用以下工具：
- search: 搜索最新信息
- calculator: 计算

任务：评估"某 AI 创业公司 A"的投资价值。

已知信息：
- 公司 A 成立于 2022 年，专注于大模型应用
- 目前已获得 A 轮融资，金额未知

请通过以下步骤评估：

请按 ReAct 格式执行每一步。
```

### 2.6 Tree-of-Thought（思维树）

**核心原理**：将问题分解为多个可能的解决路径（思维树），对每条路径进行评估，选择最优路径得到最终答案。适合需要探索多种可能性的任务。

#### 基础格式

```
任务：[复杂任务]

请按照思维树方法：

步骤 1：提出 3-5 种可能的解决思路/方案
步骤 2：对每种思路进行初步评估（可行性、优缺点）
步骤 3：选择 1-2 种最优思路深入发展
步骤 4：对深入发展的思路进行细化
步骤 5：综合比较，给出最终方案

对于评估，请考虑：
- 可行性（1-5 分）
- 成本（1-5 分，1=低成本）
- 预期效果（1-5 分）
```

#### 实战案例 1：产品设计决策

```
任务：设计一款面向开发者的 AI 辅助编程工具的产品功能路线图。

步骤 1：提出 3-5 种可能的产品方向
- 思路 A：[描述]
- 思路 B：[描述]
- 思路 C：[描述]

步骤 2：对每个思路评估
| 思路 | 可行性 | 成本 | 预期效果 | 差异化 |
|------|--------|------|----------|--------|

步骤 3-5：选择最优思路并细化功能列表
```

#### 实战案例 2：问题解决路径选择

```
任务：某 SaaS 公司的用户留存率连续 3 个月下降，从 45% 降至 38%，
请分析可能的原因并制定改进方案。

步骤 1：提出可能的原因假设（至少 5 个）
步骤 2：设计验证方法验证每个假设
步骤 3：根据验证结果确定主要原因
步骤 4：制定针对性的改进方案
```

#### 实战案例 3：多方案比选

```
任务：某电商平台计划提升用户购买转化率，现有以下预算 500 万。
请制定资金使用方案。

步骤 1：提出 3-5 种资金使用方案
- 方案 A：全部用于广告投放
- 方案 B：...
- 方案 C：...

步骤 2：评估每种方案
- 预期转化率提升幅度
- 所需时间
- 风险

步骤 3：选择最优方案并给出详细的执行计划
```

### 4.1 提示词链（Prompt Chaining）

**核心思想**：将复杂任务分解为多个步骤，每一步的输出作为下一步的输入。

#### 示例：长文档分析

# 步骤 1：文档摘要
输入：[完整文档]
任务：生成 200 字以内的摘要，提取核心观点。
输出：摘要

---

# 步骤 2：关键信息提取
输入：[原文 + 摘要]

### 5.2 自动化评估脚本思路

#### 5.2.1 基于规则的评估

```python
"""
自动化评估脚本示例
"""

import re
from typing import List, Dict

def evaluate_output(response: str, criteria: Dict) -> Dict:
    """
    基于规则的自动化评估
    """
    results = {}
    
    # 1. 检查是否包含关键信息
    for key_term in criteria.get('key_terms', []):
        results[f'contains_{key_term}'] = key_term.lower() in response.lower()
    
    # 2. 检查输出格式
    if criteria.get('expected_format') == 'json':
        results['is_valid_json'] = is_valid_json(response)
    
    # 3. 检查长度
    word_count = len(response.split())
    if 'min_length' in criteria:
        results['meets_min_length'] = word_count >= criteria['min_length']
    if 'max_length' in criteria:
        results['meets_max_length'] = word_count <= criteria['max_length']
    
    # 4. 检查特定模式
    for pattern_name, pattern in criteria.get('patterns', {}).items():
        results[pattern_name] = bool(re.search(pattern, response))
    
    # 5. 负面模式检查
    for neg_pattern_name, neg_pattern in criteria.get('negative_patterns', {}).items():
        results[f'no_{neg_pattern_name}'] = not re.search(neg_pattern, response)
    
    return results

def calculate_score(results: Dict, weights: Dict) -> float:
    """
    根据评估结果和权重计算总分
    """
    score = 0.0
    total_weight = 0.0
    for key, weight in weights.items():
        if key in results:
            score += (1.0 if results[key] else 0.0) * weight
            total_weight += weight
    return score / total_weight if total_weight > 0 else 0.0


# 使用示例
criteria = {
    'key_terms': ['解决方案', '步骤', '建议'],
    'expected_format': 'markdown',
    'min_length': 100,
    'max_length': 1000,
    'patterns': {
        'has_heading': r'^# ',
        'has_list': r'^-\s',
    },
    'negative_patterns': {
        'no_hallucination': r'编造|虚构|可能不准确',
    }
}

response = """
# 解决方案

以下是详细的步骤：
- 第一步...
- 第二步...

建议：...
"""

results = evaluate_output(response, criteria)
score = calculate_score(results, {'contains_solution': 0.3, ...})
print(f"评分: {score:.2f}")
```

## 第七部分：常见陷阱与调试技巧

### 7.1 常见陷阱（15 个）

#### 陷阱 1：提示词过于模糊

**问题**：
```
请帮我写一篇文章。
```

**问题所在**：没有主题、没有字数、没有风格、没有目标读者。

**修复**：
```
请帮我写一篇关于"远程办公对团队协作影响"的文章。
- 目标读者：企业管理者
- 字数：800-1000 字
- 风格：专业、有数据支持
- 结构：引言 → 现状分析 → 影响分析 → 建议
```

---

#### 陷阱 2：指令冲突

**问题**：
```
用中文回答。同时，使用正式的美国商务邮件格式。
```

**问题所在**：语言要求和文化格式冲突。

**修复**：
```
用中文书写，但采用正式商务邮件的结构：
- 称谓
- 正文
- 结尾敬语
```

---

#### 陷阱 3：一次性给出太多要求

**问题**：
```
写一篇关于 AI 的文章，要包括历史、技术原理、应用案例、
未来趋势、伦理问题、政策法规、市场分析、竞争格局、
技术挑战、用户教育、人才需求、投资情况、社会影响...
（共 30 个要求）
```

**问题所在**：超出模型注意力范围，部分内容被忽略。

**修复**：
```
分步进行：

第一步：请撰写 AI 发展简史（500 字）
第二步：基于上面的内容，补充技术原理和应用案例
第三步：在之前的基础上，补充未来趋势和伦理问题
```

---

#### 陷阱 4：忽略模型限制

**问题**：
```
请列出 2024 年 12 月最新发布的 iPhone 的所有技术参数。
```

**问题所在**：模型知识截止时间之前的事件，无法获取。

**修复**：
```
请基于我的信息进行分析：
我了解到 2024 年 12 月发布了 iPhone 16 系列，
主要变化包括 A18 芯片和新的摄像头系统。
请帮我分析这些变化对用户体验的可能影响。
```

---

#### 陷阱 5：期望精确数字

**问题**：
```
2024 年全球新能源汽车销量是多少？请给出精确数字。
```

**问题所在**：模型可能编造数字。

**修复**：
```
请告诉我你对 2024 年全球新能源汽车销量的了解。
如果不确定精确数字，请说明你的信息来源或估算方法。
```

---

#### 陷阱 6：角色设定不匹配

**问题**：
```
你是一位专业的厨师。请帮我写一段 Python 代码。
```

**问题所在**：角色与任务不匹配。

**修复**：
```
你是一位擅长编程的计算机科学家。请帮我写一段 Python 代码...
```

---

#### 陷阱 7：Few-shot 示例质量差

**问题**：
```
示例 1：输入：你好 → 输出：你好
示例 2：输入：再见 → 输出：再见
输入：谢谢 → 输出：
```

**问题所在**：示例没有展示任务模式，过于简单。

**修复**：
```
示例 1：
输入：用户反馈：产品很好用，但价格有点贵。
输出：{"sentiment": "mixed", "pros": ["产品好用"], "cons": ["价格贵"]}

示例 2：
输入：用户反馈：物流太慢了，等了 5 天。
输出：{"sentiment": "negative", "pros": [], "cons": ["物流慢"]}

输入：用户反馈：包装精美，打开时很有仪式感。
输出：
```

---

#### 陷阱 8：Chain-of-Thought 使用不当

**问题**：
```
请逐步思考并回答：2+2 等于几？
```

**问题所在**：简单问题不需要推理过程，反而浪费 token。

**修复**：
```
对于简单问题直接回答：
2 + 2 = 4

对于复杂问题才使用思维链：
请逐步推导：347 × 89 = ?
```

---

#### 陷阱 9：忽略输出格式

**问题**：
```
请分析以下数据并给出建议。
```

**问题所在**：没有指定输出格式，结果可能不符合后续处理需求。

**修复**：
```
请分析以下数据并给出建议。
输出格式要求：
1. 先给出 3 个核心发现（每点不超过 20 字）
2. 然后用表格列出详细分析
3. 最后用编号列表给出 3-5 条建议
```

---

#### 陷阱 10：温度设置不当

**问题**：
```
Temperature = 0.9（用于数据提取任务）
```

**问题所在**：高温度导致输出不稳定。

**修复**：
```
数据提取任务应使用低温度（0.1-0.2），确保一致性。
创意写作任务可使用高温度（0.7-0.9）。
```

---

#### 陷阱 11：缺乏负面约束

**问题**：
```
请介绍这家公司的业务。
```

**问题所在**：没有说明不需要什么内容。

**修复**：
```
请介绍这家公司的业务。
注意事项：
- 不要包含虚构的财务数据
- 不要引用不确定的信息来源
- 如果信息不在你的知识库中，请直接说明
```

---

#### 陷阱 12：上下文窗口溢出

**问题**：
```
（发送 20000 字的文档，要求模型分析其中的某个细节）
```

**问题所在**：关键信息被截断或淹没在长上下文中。

**修复**：
```
方法 1：将文档分段处理，每次处理一个章节
方法 2：先让模型生成摘要，再针对摘要提问
方法 3：提取需要分析的具体段落，而非整个文档
```

---

#### 陷阱 13：多轮对话上下文丢失

**问题**：
```
（新对话中直接引用之前对话的决策）
```

**问题所在**：模型没有跨会话记忆。

**修复**：
```
在对话开始时提供上下文摘要：
"我们之前讨论了项目 A 的预算问题，已决定：
- 总预算：100 万
- 分配：研发 60%，市场 30%，运营 10%
现在我想讨论..."
```

---

#### 陷阱 14：幻觉未被检测

**问题**：
```
（使用模型生成的看似合理但实际错误的信息）
```

**问题所在**：没有验证机制。

**修复**：
```
添加验证提示：
"请检查以下信息：
1. 所有数据和数字必须有来源说明
2. 引用必须真实存在
3. 如有不确定内容，请标注'需要验证'
4. 最后列出所有需要用户自行验证的要点"
```

---

#### 陷阱 15：缺乏迭代意识

**问题**：
```
（期望一次提示就得到完美结果）
```

**问题所在**：好的提示词需要迭代优化。

**修复**：
```
采用迭代优化流程：
第一轮：基础提示 → 获得初步结果
第二轮：分析不足 → 添加改进指令
第三轮：测试变体 → A/B 对比
持续：记录有效模式，形成提示词库
```

### 7.2 调试技巧（15 个）

#### 技巧 1：分步验证法

当结果不理想时，将复杂提示分解为多个步骤，逐个验证。

```
完整提示 → 分解为：
1. [第一步] 先确认模型是否正确理解任务
2. [第二步] 再检查模型是否正确提取信息
3. [第三步] 最后检查模型是否正确推理

每步单独测试，定位问题环节。
```

---

#### 技巧 2：变量替换法

通过替换提示词中的变量，观察输出变化，识别敏感点。

```
原始提示：请为{产品}撰写营销文案。

测试变量：
- {产品} = "iPhone"
- {产品} = "牙膏"
- {产品} = "咨询服务"

观察：
- 是否某些产品类型效果更好？
- 输出风格是否一致？
- 哪些变量需要更多上下文？
```

---

#### 技巧 3：对比测试法

同时测试多个提示词变体，找出最优方案。

```
版本 A：直接指令
版本 B：角色设定 + 指令
版本 C：角色设定 + Few-shot + 指令

输出对比：
| 维度 | A | B | C |
|------|---|---|---|
| 准确性 | 3 | 4 | 5 |
| 一致性 | 4 | 4 | 5 |
| 有用性 | 3 | 4 | 4 |
```

---

#### 技巧 4：反例检测法

专门测试模型容易出错的情况。

```
测试反例：
1. 边界情况：空输入、超长输入、特殊字符
2. 冲突输入：相互矛盾的要求
3. 诱导性输入：故意引导错误输出
4. 格式异常：格式不规范的输入

记录失败案例，完善提示词。
```

---

#### 技巧 5：思维链可视化

让模型展示推理过程，便于调试。

```
请在回答前展示你的思考过程：
1. 我理解的问题是...
2. 我需要考虑的因素是...
3. 我采用的方法是...
4. 我的结论是...

如果思考过程出错，可以针对性修正。
```

#### 技巧 6：中间输出检查

在长提示词链中，检查中间步骤的输出。

```
步骤 1 输出：{检查是否正确}
步骤 2 输出：{检查是否依赖了正确的步骤 1}
步骤 3 输出：{检查逻辑是否连贯}

在某一步出错时，固定该步骤的输入和输出。
```

#### 技巧 7：温度敏感性测试

测试不同温度设置对输出的影响。

```
Temperature = 0.1：检查一致性
Temperature = 0.5：检查平衡性
Temperature = 0.9：检查创造性

记录不同温度下的输出差异，确定最佳温度。
```

#### 技巧 8：示例增强法

当 Few-shot 效果不佳时，增加示例数量或质量。

```
问题：模型总是忽略某个约束。

解决方案：
1. 在更多示例中强调该约束
2. 创建一个专门展示该约束的示例
3. 在提示词开头和结尾都强调该约束
```

---

#### 技巧 9：约束显式化

将隐含的约束变为显式的规则。

```
隐含：不要编造信息
显式：如果信息不在你的知识范围内，请明确说"我不知道"，
      不要编造数字、日期或引用。
```

#### 技巧 10：格式模板法

当输出格式不稳定时，提供明确的格式模板。

```
输出格式必须严格遵守以下模板：

```json
{
  "summary": "字符串",
  "points": ["字符串 1", "字符串 2", "字符串 3"],
  "confidence": 0.0-1.0 的数字
}
```

不要添加额外的字段，不要修改字段名称。
```

#### 技巧 12：负面示例法

明确告诉模型"不要做什么"。

```
不要这样做：
- 不要使用模糊的表述如"可能"、"大概"
- 不要编造数据或引用
- 不要在不确定时强行给出答案

正确的做法是：
- 明确说明信息的不确定性
- 标注需要验证的内容
- 优先提供可验证的信息
```

方法 4：分批次处理，保留状态

关键原则：只传递对当前任务必要的信息。
```

请以以下格式输出：
### 初稿

...
### 修正说明
...
### 最终答案
...
```
